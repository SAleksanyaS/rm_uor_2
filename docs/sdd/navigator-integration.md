# Версионные снимки отчётов и паспорт Навигатора

Статус документа — проект для согласования. Основание — встреча 13 ноября 2026 года и [этапы 3–4 плана](../plans/2026-11-16-dit-overview-and-reports.md). На встрече обсуждали действующий пример ДИТ сервисов, выбор исторического среза по дате и использование одного подготовленного набора в карте целей и отдельном отчёте. Формат, способ доставки, роли и доступы требуют согласования. Временные отметки записи — 10:28:23–10:29:06, 10:45:57–10:50:47, 11:00:26–11:01:22 и 11:32:00–11:33:04.

## Пилот в рабочем месте

Куратор выбирает загруженную книгу XLSX в «Статусах ДИТ» либо указывает основание ручного факта. Он сверяет дату измерения, план и факт. Период задаёт деловую область оценки, например `Q4 2026` или `Y26`. Дата записи фиксирует момент сохранения результата. Эти поля могут различаться.

При сохранении создаётся отдельное версионное измерение для пары `goalId` и `period`. Технический формат выгрузки пилота содержит следующие поля.

| Поле | Содержание |
| --- | --- |
| `schemaVersion` | Версия формата пилота, `1` |
| `goalId`, `period` | Код цели в карте и отчётный период |
| `measurement.id` | Идентификатор сохранённого измерения |
| `measurement.method` | `manual-v1`, `xlsx-cell-v1` или `xlsx-ratio-v1` |
| `measurement.asOf`, `measurement.unit`, `measurement.plan`, `measurement.fact` | Дата измерения, единица, числовой план или `null`, числовой факт |
| `measurement.origin` | Ручной факт хранит ссылку или описание подтверждающего источника. Для XLSX — SHA-256 и имя книги, лист, адреса и значения использованных ячеек |
| `measurement.author`, `measurement.recordedAt` | Подпись автора и время сохранения |

Повторная выгрузка одного сохранённого измерения даёт тот же JSON. ID измерения считается по бизнес-полям, включая план, факт, единицу и происхождение. Подпись автора, время записи и имя файла исключены из расчёта ID. Опубликованное измерение сохраняется с исходной версией метода. Для `xlsx-ratio-v1` используются целые числитель и знаменатель, значение от 0 до знаменателя и знаменатель больше нуля. Результат выражается в процентах с округлением до шести знаков после запятой.

Расчёт выполняется локально. Отдельное измерение ДИТ можно опубликовать через [существующий Git-обмен](data.md#общий-git-файл-и-копия). Для приёмки «Года качества» нужны две датированные выгрузки, действующий расчёт и ожидаемые значения. Исторический PDF «Года качества» служит контрольным справочным примером после сверки периода и периметра. Автоматическое подключение к Навигатору и обмен многодатными наборами отчётов остаются отдельной задачей.

## Предлагаемый контракт обмена

| Поле конверта | Правило |
| --- | --- |
| `schemaVersion` | Версия схемы обмена. Потребитель проверяет её до применения |
| `reportId` | Стабильный код направления, согласованный владельцем |
| `period`, `asOf` | Отчётный период и подтверждённая календарная дата среза в формате `YYYY-MM-DD` |
| `snapshotId` | SHA-256 содержимого конверта без поля `snapshotId`, после согласованной сериализации |
| `supersedes` | Идентификатор прежнего снимка для исправления того же `reportId`, периода и даты, либо `null` |
| `measurements` | Измерения в согласованном формате пилота. Для каждой записи указаны цель, метод и происхождение. Дубликаты ключей внутри набора отклоняются |

Для расчёта `snapshotId` предлагается UTF-8 без BOM, сортировка ключей объектов и элементов `measurements` по паре `goalId`, `period` и согласованное представление чисел. Другие массивы сохраняют порядок, если он имеет деловой смысл. Перед подключением нужны два контрольных файла и одинаковый результат хеширования у поставщика и потребителя. Идентификатор фиксирует байты согласованного содержания. Версия схемы управляет совместимостью, версия метода объясняет расчёт, дата среза определяет период сравнения внутри серии.

### Доставка и история

1. Поставщик передаёт согласованный минимум измерений. Потребитель проверяет формат, идентификатор, уникальность записей и связь с предыдущей версией, затем применяет набор целиком.
2. Повтор того же ID считается повторной доставкой. Исправление даёт новый ID и ссылается на предыдущий ID через `supersedes`. Обе версии доступны для просмотра с исторической датой среза.
3. Две исправленные версии с одной базой требуют решения владельца. Неподдерживаемая схема, повреждённый файл или ошибка сверки оставляют последний принятый снимок и дают явную диагностику.
4. Карта и отдельный отчёт используют один идентификатор принятого снимка. На карте числовой факт ДИТ появляется из отдельного измерения ДИТ. Для назначения лидера используется измерение соответствующего уровня, когда оно входит в согласованную схему. Публикация статуса цели остаётся в действующем [Git-обмене статусами](data.md).

Если владельцы выберут общий репозиторий как транспорт, предлагаем путь `reports/<report-id>/<period>/<as-of>/<snapshot-id>.json`. Для имён каталогов нужны стабильные ASCII-коды, например `year-of-quality/q4-2026/2026-11-13/`. Файл пишется один раз. Его правила размещения, допустимые данные, ветку, согласование и порядок исправления фиксируют в СберТреке. Первичные XLSX и доступ к ним остаются в согласованном исходном хранилище. Ссылка на источник ограничивается метаданными, необходимыми для сверки и разрешёнными к передаче.

## Паспорт Навигатора

| Поле | Известно | Открыто к согласованию |
| --- | --- | --- |
| Назначение | Исторические отчёты направлений. Встреча опиралась на пример ДИТ сервисов | Точная ссылка, пространство, витрина и эталонный экран |
| Поставщики и потребители | Владельцы направлений подготавливают результаты. Карту и отчёт рассматривают как потребителей общего снимка | Поимённые владельцы отчётов и данных, кто принимает исправления, кто сопровождает загрузку |
| Источники | Пилот начинается с датированных XLSX и контрольного результата. На встрече обсуждали ОКО и обогащение | Список первичных отчётов, фильтры, ключи, ответственные, разрешённый доступ и режим обновления |
| Формат и доставка | У пилота есть локальная выгрузка JSON. На встрече обсуждались SQL и репозиторий | Поддерживаемые интерфейсы Навигатора, формат и схема загрузки, ветка или другой канал, квоты, способ подтверждения доставки |
| История | Срезы различаются по датам | Правила времени и опоздавших данных, реестр принятых версий, срок хранения, отзыв и восстановление |
| Доступ и эксплуатация | Приёмка проводится на разрешённом рабочем устройстве | Кто выдаёт права чтения и записи, служебная или личная учётная запись, тестовый контур, поддержка при сбое |
| СберТрек | На встрече попросили страницу с паспортом, структурой папок и правилами сохранения | Ссылка и владелец страницы, согласованный текст и дата проверки |

## Приёмка

| Сценарий | Что проверяем |
| --- | --- |
| Два датированных XLSX | Владелец подтверждает период, состав данных и ожидаемые значения каждого среза. Смена файла воспроизводится без ручного копирования ячеек |
| Повторный запуск | Те же байты входа и версия метода дают те же бизнес-значения. Повторный экспорт сохранённого ID даёт тот же JSON |
| Повтор доставки и исправление | Повтор не создаёт копию. Исправление сохраняется новым снимком. Старый снимок читается по своему ID. Параллельные исправления требуют сверки |
| Ошибка и доступ | Неизвестная схема, отсутствующий операнд, повтор ключа и отказ доступа дают диагностику. Последний принятый снимок читается |
| Один поток до двух экранов | В целевой среде карта и отчёт читают один принятый ID, показывают согласованные значения и открывают нужную дату. Сверяются права и действующий пример ДИТ сервисов |
